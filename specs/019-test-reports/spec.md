# 功能规范：019 本次执行的测试报告与发布证据

**Feature Branch**: `019-test-reports`
**Created**: 2026-10-04
**Status**: 规范/规划与实现完成，基线008已验收；019实际验收通过，正式收敛无缺口，待整功能提交
**Input**: 全MVP目标及CONFIGURATION“测试报告”规划。复用003独立产物快照与007唯一执行/中央文件路径；测试失败不得进入发布，不以旧报告或post诊断放行。

## User Scenarios & Testing

### User Story 1 - 读取本次执行的测试结果 (Priority: P1)
开发者声明每个build的JUnit路径，本地或节点执行后得到正确的用例总数、失败、错误、跳过、耗时及受限失败摘要，原报告可核对。
**Why this priority**: 脚本成功退出不能代表测试通过，报告必须属于本次执行。
**Independent Test**: 用实际脚本生成通过/失败/错误/跳过报告，重复改写同路径及嵌套suite，核对摘要和原始快照。
**Acceptance Scenarios**:
1. 合法testsuite/testsuites报告汇总实际用例，嵌套suite和同路径多次读取不重复计数，改写后替换该路径结果。
2. 测试命令非零仍尝试收集已有新报告，保留原命令失败；零退出但失败/错误用例使构建失败。
3. 摘要含总数/失败/错误/跳过/耗时及受限诊断，原XML保留大小/摘要对应独立快照，后续源修改不改变证据。

### User Story 2 - 拒绝旧报告与不安全内容 (Priority: P1)
开发者在已有工作树调试时，旧报告不能被误认作本次通过；非法XML、缺失或越界均有明确结果。
**Why this priority**: 用户可以反复本地运行，报告存在本身不足以放行发布。
**Independent Test**: 真实预置旧文件、重写/新建/替换、symlink/FIFO/越界、坏XML与有界大文件，核对无副作用及安全失败。
**Acceptance Scenarios**:
1. 本地开始前记录匹配文件身份/修改时间/摘要，只接受本次新建或改写；旧文件不删除、不计入，--step亦不能借旧报告通过。
2. required默认true，缺失在普通执行结束或发布边界失败；required=false只允许缺失，存在的非法报告依然失败，命令非零不能被允许缺失覆盖。
3. 路径/文件/内容有界，拒绝越界、符号链接、不普通文件、非法结构及矛盾计数，不读取外部实体或联网，安全输出不泄秘密或原工作区路径。

### User Story 3 - 及时阻止后续动作并固定报告结果 (Priority: P1)
开发者希望准备步骤没有报告时继续，但已生成失败报告时停止后续普通动作；普通结果确定后才选择post，post不能改变发布放行依据。
**Why this priority**: 报告检查到上传之后才进行，无法阻止失败版本被发送。
**Independent Test**: 真实准备→测试→哨兵及success/failure/always链路；在准备缺失、失败报告和post改写场景核对哨兵、预算与结果。
**Acceptance Scenarios**:
1. 每个普通run结束检查已生成新报告，准备步骤尚无报告不误失败；发现失败/错误/非法报告停止后续普通动作，最终required规则仍执行。
2. 普通执行结束根据命令及报告结果选择success/failure/always；post写通过报告不能把失败改成功，post失败或取消不覆盖原报告证据。
3. 同一执行保留普通阶段报告通过/失败结论及产物标识/摘要；后续发布审批/首次上传须核对该证据，当前尚未实现的approval/upload继续明确拒绝，不能提前放行。

### User Story 4 - 查询本地与中央的可核对证据 (Priority: P1)
管理员通过构建详情/JSON查看报告摘要和原XML；节点离线后中央已确认报告仍可下载，其归属和完整性受已有权限保护。
**Why this priority**: 构建状态、报告计数和原文件须能在同一执行内追溯。
**Independent Test**: 本地结果查询、实际macOS/Linux节点报告回传、两个数据库同套查询、节点离线中央下载及身份负例。
**Acceptance Scenarios**:
1. 本地与远程详情/JSON呈现同一报告结论、来源执行/路径对应的受限身份和原始报告元数据，不混其它build/attempt或未确认文件。
2. 完整回传并核对后中央原XML可下载，节点离线不影响；坏内容、缺少文件、旧租约或只有报告摘要不算完整终态证据。
3. 管理/审批身份可以查询下载，trigger/节点身份不能越权读取；失权或持久化失败停止新用户动作，不重放报告检查或重置执行预算。

### Edge Cases
- 脚本非零却有通过报告、脚本零退出有失败报告、准备步骤无报告、required=false遇到坏文件、取消/失权期间收集。
- 嵌套suite汇总属性与case重复、同路径改写/删除/同内容重建、旧文件、空报告、错误负数/无限耗时、巨大失败文本。
- 相同仓库多个build独立工作区、XML外部实体/DOCTYPE/恶意深度、symlink/FIFO/报告与源被改写、快照写失败。
- 普通结束后post改写XML、回传丢响应/旧fence、中央文件缺失/坏摘要、节点离线及身份边界。

## Requirements

### Functional Requirements
- **FR-001**: 单流水线或命名build支持reports.junit.paths与required，required默认true；无报告配置时既有执行行为保持，不增加普通步骤类型。
- **FR-002**: 接受JUnit testsuite/testsuites并汇总总数/失败/错误/跳过/耗时及受限失败摘要；嵌套汇总不重复计算，非法结构/值或矛盾计数不能作为通过依据。
- **FR-003**: 按报告相对路径维护本次结果，同路径再次解析替换原记录而非累加，执行终态和原始快照使用最终普通阶段对应内容。
- **FR-004**: 每个普通run结束后检查已生成的本次报告，命令失败也尝试收集；发现失败/错误/非法内容立即停止后续普通动作，保留原命令失败原因。
- **FR-005**: 准备步骤未生成报告不因required提前失败；普通执行结束或进入发布边界检查缺失，required=false只允许缺失，不豁免非法XML/路径/命令失败。
- **FR-006**: 本地开始前记录匹配文件身份/修改时间/摘要，只收本次新建或改写，不删除用户旧文件；--step使用相同新鲜性和required规则，不借旧产物/报告放行。
- **FR-007**: 节点使用007受控全新工作区并绑定固定build/attempt/lease，只收本执行报告；同仓库多build不得互相取报告或扩大访问范围。
- **FR-008**: 报告路径/匹配/文件/解析深度/用例数量/摘要/耗时有界，复用普通文件、符号链接和越界保护；不解析外部实体、不网络读取，恶意内容/超限明确失败。
- **FR-009**: 原XML复用独立快照、大小/摘要与中央完整文件确认，不直接从可变工作区下载，不以摘要替代原文件，源篡改不能改变已确认数据。
- **FR-010**: 摘要按已声明秘密脱敏；原XML含声明秘密时安全失败且不回传，不能通过失败文本、属性或路径把凭据输出到公共结果。可下载原XML保持原字节及对应摘要，不重写报告伪造原始证据。
- **FR-011**: 普通命令/报告结果先确定，再选择post；post仅产生诊断，不改写普通报告或后续放行证据，不把报告失败降为警告/unstable后继续。
- **FR-012**: 保存同一执行的报告结论与原文件受限身份/摘要，给后续发布审批/首次上传核对；变化或缺失不得放行，多次上传消费同一封存证据，不新建未实现发布能力。
- **FR-013**: 复用唯一执行内核、逐动作进度、累计普通/post预算与独立执行权；报告收集/保存失败或失权禁止后续用户动作，保留真实清理/停止保护，不自动重跑。
- **FR-014**: 本地结果与中央构建详情/JSON显示报告摘要、计数、耗时、受限失败诊断和可下载原始报告元数据；安全错误不包含rawXML、秘密或私有绝对路径。
- **FR-015**: 中央报告读权限沿007管理员/审批身份，trigger/节点身份不得越权；节点离线后完整确认的文件仍可下载，旧fence/冲突/部分回传不得写入可信终态。
- **FR-016**: 两种数据库使用相同报告归属/完整性/权限/状态检查，实际本地和远程macOS/Linux脚本生成报告闭环，不把模拟执行、编译或未确认文件作为证据。
- **FR-017**: 包含最小真实行为检查：正常及异常报告、新鲜性/重复汇总、发布哨兵/post、输入边界、秘密、租约/持久化与中央下载，回归既有无报告流水线。
- **FR-018**: 007实际验收后才实现；规范/计划/任务/验证、README/历史完整，必要全量/vet/race与converge通过后整功能一次本地提交，无push。后续恢复/商店/审批验收门不缩减。

### Key Entities
- 执行报告集合：同build/attempt下按相对路径替换的本次报告与新鲜性证据。
- 报告摘要：正确计数/耗时/通过结论及受限诊断，不是未经验证的脚本退出状态。
- 原始报告快照：安全下载内容、大小/摘要及确认身份，与普通阶段结论绑定。
- 发布证据：同执行封存报告和产物引用，后续发布前核对，不提供当前未实现动作。

## Success Criteria

### Measurable Outcomes
- **SC-001**: 通过/失败/错误/跳过及嵌套/同路径替换样例计数、耗时和失败结论全部准确且不重复，原报告内容可核对。
- **SC-002**: 旧文件、缺失/非法/越界/实体/超限等负例不能成为通过证据；用户旧工作树保持，required=false不掩盖失败。
- **SC-003**: 失败报告后的普通哨兵不执行，准备步骤缺失不误阻断；普通结果正确选择post，post改写不改变原放行证据。
- **SC-004**: 本地与实际远程节点的详情/下载一致，节点离线可读；旧执行、错误身份、坏中央文件及部分回传均拒绝。
- **SC-005**: 相同测试两库状态一致，秘密不出公共输出或下载证据；累计预算、取消、失租及无报告既有行为回归通过。
- **SC-006**: 所有需求与验收场景有实际记录、必要检查和收敛无缺口，整功能规范/任务/代码/验证与本地提交可追溯，未实现发布仍明确失败。

## Assumptions
- 已授权产品设计规定不增加unstable状态或测试平台；保留原四种普通步骤，本功能增加报告解释与证据。
- 003、007、008已验收，019以008提交504dc6为正式基线实施，必须先于010/011。
- 失败诊断脱敏；含声明秘密的原XML不作为公开下载产物。合法可下载XML保持原字节/摘要与计数对应，避免重写原报告改变证据。
- 格式/安全具体限额在plan冻结，所有生效reports不得继续按“unsupported”运行；未配置reports不读任意报告文件。
- 后续商店与审批尚未实现，本功能验收通过结论/封存引用和哨兵拒绝，不虚构真实商店放行证据。
